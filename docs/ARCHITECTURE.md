## 1. Overview

The architecture mirrors Power BI's internal split:

| In Power BI | In Measura |
|---|---|
| Mashup engine (Power Query / M) | M interpreter that compiles to SQL |
| VertiPaq (storage engine) | **DuckDB** |
| Formula engine (DAX) | DAX engine in **Rust** |
| Power BI Desktop UI | **React** inside **Tauri** |

The central idea is that **every visual is a DAX query**. A chart with `Product[Category]` on the axis and `[Total Sales]` as values, filtered by a year slicer, internally generates:

```dax
EVALUATE
SUMMARIZECOLUMNS(
    Product[Category],
    TREATAS({2025}, Calendar[Year]),
    "Total Sales", [Total Sales]
)
```

Power BI does exactly this. With this choice, the DAX engine serves both measures and visuals.

```
┌──────────────────────────────────────────────────────────────────────┐
│ UI (React + Tauri)                                                   │
│ Report │ Table │ Model │ Power Query editor                          │
└──────────────┬──────────────────────────────────────┬────────────────┘
               │ DAX query generated by the visual     │ M code
┌──────────────▼──────────────────────┐  ┌─────────────▼───────────────┐
│ DAX engine (formula engine)         │  │ M engine (mashup)           │
│ parser → plan → SQL + evaluator     │  │ parser → steps → SQL        │
└──────────────┬──────────────────────┘  └─────────────┬───────────────┘
               │ SQL                                   │ load
┌──────────────▼───────────────────────────────────────▼───────────────┐
│ DuckDB (storage engine)                                              │
└──────────────────────────────────────────────────────────────────────┘
```

**Design rules:**

- The core (M, DAX, model, execution) is a **headless Rust library**. The same library runs on desktop, on the server and in the browser (WASM).
- The UI never generates SQL. It generates **DAX and M**, as Power BI does.
- Projects are saved as **PBIP/TMDL** (see [section 7](#7-project-format)).

## 2. Storage engine

**DuckDB** replaces VertiPaq:

- Columnar, vectorized analytical database, very fast at aggregations
- Embedded in the app, no separate server
- Reads CSV, Excel, Parquet and JSON, and connects to Postgres, MySQL, SQL Server and SQLite
- Available for Rust (`duckdb-rs`) and the browser (`duckdb-wasm`)

| Power BI mode | Implementation |
|---|---|
| **Import** | Tables loaded into a `.duckdb` file in the project's cache folder |
| **DirectQuery** | SQL sent to the original source. Later phase |
| **Dual / Composite** | Out of initial scope |

## 3. Power Query and M

### 3.1 How it works

As in Power BI, **every click in the UI generates an M step**:

```m
let
    Source = Csv.Document(File.Contents("data/sales.csv"), [Delimiter=",", Encoding=65001]),
    #"Promoted Headers" = Table.PromoteHeaders(Source, [PromoteAllScalars=true]),
    #"Changed Type" = Table.TransformColumnTypes(#"Promoted Headers",
        {{"Date", type date}, {"Amount", type number}}),
    #"Filtered Rows" = Table.SelectRows(#"Changed Type", each [Amount] > 0),
    #"Removed Columns" = Table.RemoveColumns(#"Filtered Rows", {"Notes"})
in
    #"Removed Columns"
```

- Each `let` variable appears in the **Applied Steps** pane
- The gear next to each step reopens the dialog that created it
- The **Advanced Editor** shows and edits the M code directly
- The formula bar shows the M of the selected step

### 3.2 Execution

```
M code ──► parser ──► AST ──► Table.* function recognizer ──► typed steps ──► DuckDB SQL
                                        │
                                        └─ unrecognized expressions ──► M interpreter (row by row)
```

- **Common case:** `Table.*` functions become SQL CTEs, the equivalent of *query folding*
- **Database sources:** the initial steps are pushed down to the database itself
- **Simple `each` expressions** (`[Amount] > 0`, `Text.Upper([Name])`) are translated to SQL
- **Complex cases** (custom functions, `List.Accumulate`, recursion) go to an M interpreter in Rust, slower but correct
- Preview runs on a sample; **Close & Apply** performs the full load

### 3.3 Functions by phase

| Phase | Functions |
|---|---|
| **v1** | Sources: `Csv.Document`, `Excel.Workbook`, `Parquet.Document`, `Folder.Files`, `Sql.Database`, `PostgreSQL.Database`. Table: `PromoteHeaders`, `TransformColumnTypes`, `SelectRows`, `RemoveColumns`, `SelectColumns`, `RenameColumns`, `ReorderColumns`, `Distinct`, `Sort`, `FirstN`, `AddColumn`, `ReplaceValue` |
| **v2** | `NestedJoin` + `ExpandTableColumn` (merge), `Combine` (append), `Group`, `UnpivotOtherColumns`, `Pivot`, `SplitColumn`, `TransformColumns`, `FillDown`, `Transpose`. Most used `Text.*`, `Date.*`, `Number.*` functions |
| **v3** | Parameters, custom functions, `List.*`, `Record.*`, `Web.Contents`, `Json.Document`, combine files from a folder |

### 3.4 Editor UI

- Queries pane on the left, preview grid in the center, **Query Settings** and **Applied Steps** on the right
- Ribbon with the Home, Transform, Add Column and View tabs
- **Column quality, distribution and profile** below the headers
- Type icon in each column header, which also changes the type

## 4. Semantic model

The model follows Power BI's concepts without adaptation:

- **Relationships:** cardinality (1:1, 1:N, N:1, N:N), cross-filter direction (single or both), active or inactive
- **Date table:** "Mark as date table"
- **Calculated columns:** DAX evaluated row by row at load time and materialized
- **Calculated tables:** DAX returning a table (`CALENDAR`, `SUMMARIZE`, etc.)
- **Hierarchies**, **display folders**, **sort by column**, **hidden** columns and tables
- **Format** and **data category** (currency, percentage, country, image URL...)
- **RLS roles** with DAX filters
- **Relationship autodetection** on load, like the Power BI option

## 5. DAX engine

This is the most critical component. The goal is to **produce the same results as Power BI**.

### 5.1 Concepts the engine implements

| Concept | Behavior |
|---|---|
| **Filter context** | Set of per-column filters coming from the visual, slicers, page and report filters, and `CALCULATE` |
| **Propagation** | Filters follow relationships from the one side to the many side (or both ways, if configured) |
| **Row context** | Created by iterators (`SUMX`, `FILTER`, `ADDCOLUMNS`) and calculated columns |
| **Context transition** | `CALCULATE` and every measure reference turn the row context into a filter context |
| **Modifiers** | `ALL`, `ALLEXCEPT`, `REMOVEFILTERS`, `KEEPFILTERS`, `USERELATIONSHIP`, `CROSSFILTER` |
| **BLANK** | Its own semantics (`BLANK() + 1 = 1`, `BLANK() = 0` is true), different from SQL NULL |
| **Auto-exist** | Combinations of columns from the same table that do not exist in the data are omitted |
| **Blank row** | Virtual row added to the one side when the many side has unmatched values |

### 5.2 Pipeline

The engine mirrors Power BI's split between formula engine and storage engine:

```
DAX text
   │  lexer + parser (hand-written Pratt parser, with clear error messages)
   ▼
AST ──► name and type resolution (tables, columns, measures, variables)
   │
   ▼
logical plan (Scan, Filter, Join, Aggregate, SetFilterContext, Iterate, ...)
   │
   ├──► SQL compiler ──► DuckDB         (storage engine: bulk aggregations)
   └──► Rust evaluator                  (formula engine: iterators, context
                                         transition, logic that is not plain SQL)
```

The optimizer's goal is to push as much work as possible down to DuckDB, as Power BI does with VertiPaq.

### 5.3 Compilation example

```dax
Total Sales = SUM(Sales[Amount])
% of Total  = DIVIDE([Total Sales], CALCULATE([Total Sales], ALL(Product)))
```

Visual: `Product[Category]` with both measures, slicer `Calendar[Year] = 2025`.

```sql
WITH ctx AS (
  SELECT s.*, p.Category
  FROM Sales s
  JOIN Product p  ON s.ProductId = p.Id
  JOIN Calendar c ON s.Date = c.Date
  WHERE c.Year = 2025                            -- filter propagated through the relationship
),
total     AS (SELECT Category, SUM(Amount) AS v FROM ctx GROUP BY Category),
total_all AS (SELECT SUM(Amount) AS v FROM ctx)  -- ALL(Product): removes only Product filters
SELECT t.Category,
       t.v                                       AS "Total Sales",
       CASE WHEN a.v = 0 THEN NULL ELSE t.v / a.v END AS "% of Total"   -- DIVIDE → BLANK
FROM total t CROSS JOIN total_all a;
```

### 5.4 Functions by phase

| Phase | Functions |
|---|---|
| **Essential DAX** (stage 3) | `SUM`, `AVERAGE`, `MIN`, `MAX`, `COUNT`, `COUNTA`, `COUNTROWS`, `DISTINCTCOUNT`, `CALCULATE`, `ALL`, `REMOVEFILTERS`, `FILTER`, `DIVIDE`, `IF`, `SWITCH`, `AND`, `OR`, `NOT`, `BLANK`, `ISBLANK`, `VAR/RETURN`, operators |
| **Everyday DAX** (stage 5) | `SUMX`, `AVERAGEX`, `COUNTX`, `MAXX`, `MINX`, `RELATED`, `RELATEDTABLE`, `VALUES`, `DISTINCT`, `SELECTEDVALUE`, `HASONEVALUE`, `ISFILTERED`, `ALLEXCEPT`, `ALLSELECTED`, `KEEPFILTERS`, `USERELATIONSHIP`, `CALENDAR`, `CALENDARAUTO`, time intelligence (`TOTALYTD`, `DATESYTD`, `SAMEPERIODLASTYEAR`, `DATEADD`, `PARALLELPERIOD`, `DATESINPERIOD`), text and date functions |
| **Advanced DAX** (after stage 8) | `SUMMARIZE`, `SUMMARIZECOLUMNS`, `ADDCOLUMNS`, `SELECTCOLUMNS`, `TOPN`, `RANKX`, `GENERATE`, `CROSSJOIN`, `TREATAS`, `CROSSFILTER`, `EARLIER`, `PATH*`, free-form `EVALUATE` queries |

### 5.5 Conformance with Power BI

- **Conformance suite:** cases (model + measure + filter context → expected result), with expected results generated in **real Power BI** on public datasets (AdventureWorks, Contoso)
- Runs on every change (CI). Coverage is published as a per-function **compatibility matrix**
- References: [dax.guide](https://dax.guide), Microsoft's official documentation and *The Definitive Guide to DAX* (SQLBI)
- Cross-checks: the same DAX evaluated by the SQL compiler and by the Rust evaluator must give the same result

The goal is that a Power BI user **finds everything where they expect it**.

### 6.1 Window layout

┌──────────────────────────────────────────────────────────────────────┐
│ Ribbon: Home │ Insert │ Modeling │ View │ Help                        │
├──┬─────────────────────────────────────────┬──────────┬──────────────┤
│▣ │                                         │ Filters  │Visualizations│
│▦ │          Report canvas                  │          │ [types]      │
│◫ │                                         │          │ [wells]      │
│  │                                         │          │──────────────│
│  │                                         │          │ Data         │
│  │                                         │          │ (fields)     │

### 6.2 Views

| View | What it does | Libraries |
|---|---|---|
| **Report** | Canvas with pages; Visualizations, Data, Filters and Format panes | react-grid-layout, dnd-kit, ECharts |
| **Table** | Grid of the selected table; formula bar for calculated columns and measures | Glide Data Grid, Monaco |
| **Model** | Diagram of tables and relationships; properties pane; multiple layouts | React Flow + ELK.js |
| **Power Query editor** | Separate window (see [section 3.4](#34-editor-ui)) | Glide Data Grid, Monaco |

### 6.3 Visuals

**Catalog:** table, matrix, card, multi-row card, column and bar (clustered, stacked, 100%), line, area, line and column combo, pie, donut, scatter, treemap, waterfall, funnel, gauge, KPI, map, slicer (list, dropdown, between dates, buttons).

**Behaviors to reproduce:**

- **Field wells** with the same names (X-axis, Y-axis, Legend, Values, Tooltips, Rows, Columns)
- **Implicit aggregation** when dragging a numeric column (Sum, Average, Count...)
- **Cross-filtering and cross-highlighting**, with "Edit interactions"
- **Drill down / drill up** on hierarchies and **drill-through** to another page
- **Totals and subtotals** in the matrix, with Power BI's evaluation logic (the total is the measure evaluated in the total's context, not the sum of the rows)
- **Tooltips**, **conditional formatting** and **bookmarks**
- **JSON themes** in the same format as Power BI

### 6.4 Shortcuts, terminology and languages

- Same names for menus, panes and options as Power BI, in each supported UI language (English by default, Brazilian Portuguese available)
- Equivalent keyboard shortcuts where it makes sense (`Ctrl+C`/`Ctrl+V` for visuals, `Ctrl+click` for multi-select, `Alt` for ribbon navigation)
- **Own** name, icons and visual identity: the workflow is familiar, the brand is not copied

## 7. Project format

Projects use **PBIP**, Power BI's text project format:

```
MyReport/
├── MyReport.pbip
├── MyReport.SemanticModel/
│   └── definition/
│       ├── model.tmdl
│       ├── relationships.tmdl
│       ├── tables/
│       │   ├── Sales.tmdl            # columns, DAX measures, partition with the M code
│       │   └── Product.tmdl
│       └── roles/
│           └── Regional Manager.tmdl # RLS
├── MyReport.Report/
│   └── definition/                   # pages and visuals (PBIR)
└── .cache/                           # loaded data (not in git)
```

**TMDL example** (illustrative; check against Microsoft's TMDL documentation before implementing the reader):

```tmdl
table Sales

    measure 'Total Sales' = SUM(Sales[Amount])
        formatString: "$#,##0.00"

    column Amount
        dataType: decimal
        sourceColumn: Amount

    partition Sales = m
        mode: import
        source =
            let
                Source = Csv.Document(File.Contents("data/sales.csv"), [Delimiter=","]),
                ...
            in
                #"Removed Columns"
```

- **TMDL** (model) is publicly documented by Microsoft and is the primary compatibility target
- **PBIR** (report) is read on import. Unsupported visuals show up as a placeholder with a warning, without breaking the report. PBIR is still evolving, so this is the least stable part of the plan
- **`.pbix`:** out of initial scope (binary and undocumented). The recommendation is to save as PBIP in Power BI and open it here
- Projects are versionable with git and can be **opened in both tools**, within what is supported

## 8. Publishing

The core runs in three environments, and the frontend is the same in all of them (read-only when published).

| Mode | How it works | Power BI equivalent |
|---|---|---|
| **Static site** | Exports data as Parquet + model + report. Runs in the browser with DuckDB-WASM and the DAX engine in WASM. Hosted on GitHub Pages, Netlify or S3 | "Publish to web" |
| **Self-hosted server** | Docker image: Axum API, Postgres for metadata, DuckDB per semantic model | Power BI Report Server |
| **Hosted cloud** | The same server, operated by the project | Power BI service |

**Server features**, using Power BI service concepts:

- **Workspaces** with roles (Admin, Member, Contributor, Viewer)
- **Publish** from the desktop app
- **Scheduled refresh** of the semantic model
- **RLS** using the roles defined in the model, with `USERPRINCIPALNAME()` returning the signed-in user
- **Apps** (collections of reports distributed to end users)
- Email **subscriptions** (PDF/PNG) and **embedding** via iframe with a token
- Local sign-in and OIDC/SAML (Azure AD/Entra ID, Google, Keycloak)
- **Gateway** (future phase): agent inside the customer's network to reach internal databases

## 11. Stages

The stages are the same as in the overview, here with the technical deliverables of each.

| Stage | Technical deliverables | Done when |
|---|---|---|
| **1. Foundation** | Monorepo; `model` and `engine` crates; CSV/Excel connectors; Tauri app with ribbon and the three views; table view; model view with relationships and autodetection; save and open as TMDL | Import spreadsheets, see the data, relate tables, save and reopen |
| **2. Reports** | Canvas with pages; Visualizations, Data and Filters panes; table, matrix, card, column, bar, line, pie and slicer; implicit aggregation; cross-filtering | **First report** with slicers and cross-filtering working |
| **3. Essential DAX** | `dax` crate: parser, filter propagation, SQL compilation, "essential" phase functions; Monaco formula bar; initial conformance suite | Measures like `% of Total` with `CALCULATE` + `ALL` matching Power BI |
| **4. Power Query** | `mquery` crate: M parser, v1 and v2 functions; editor window with Applied Steps, Advanced Editor and column profile; Close & Apply | Clean a messy spreadsheet with clicks only and see the generated M |
| **5. Everyday DAX** | Iterators, row context, context transition, calculated columns and tables, time intelligence; Rust evaluator; matrix with correct totals | A typical sales report (YTD, prior year, ranking) identical to Power BI |
| **6. Open Power BI projects** | Full PBIP reading (TMDL + PBIR); themes; placeholder for unsupported visuals; compatibility report on open | Open AdventureWorks saved as PBIP in Power BI and see the same measures and pages |
| **7. Publish** | `wasm` crate (DAX + DuckDB in the browser); `web` app; static export | Report published on GitHub Pages, with working filters |
| **8. Server** | `server` crate; Docker; workspaces and roles; publish from desktop; scheduled refresh; RLS; OIDC | A company starts it with `docker run`, publishes and restricts data per user via RLS |

**After stage 8:** advanced DAX, M v3, DirectQuery, gateway, full conditional formatting, bookmarks and remaining visuals, always prioritized by the compatibility matrix and user requests.

## 12. Technical risks

| Risk | Mitigation |
|---|---|
| DAX results differing from Power BI | Conformance suite with results generated in real Power BI, run on every change |
| DAX edge cases (BLANK, auto-exist, matrix totals) | Treated as explicit requirements from stage 3, with dedicated tests |
| M has hundreds of functions | Prioritize the `Table.*` functions the UI generates; interpreter as fallback; public matrix of what is supported |
| Performance below VertiPaq | Push as much work as possible to DuckDB; caching; parallel queries; benchmarks on 10M+ row datasets |
| Microsoft changing PBIP/PBIR formats | Isolated, versioned reader layer in the `report`/`model` crates; tests with files from several Power BI versions |
| Huge scope for a small team | Stages with usable deliverables; the compatibility matrix guides priorities and contributions |
| Trademark and intellectual property | Own name, icons and look; implementation from public documentation, no reverse engineering of Microsoft code |
